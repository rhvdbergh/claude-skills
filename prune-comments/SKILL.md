## Purpose

Enforce the comment rules from CLAUDE.md on real code: a comment survives only if it explains a
non-obvious *why*. Comments that restate what a line does, or narrate what was changed and for
whom, are deleted. Where a comment exists because a name is bad, the name is fixed instead.

This skill edits code directly, then reports what it removed. It does not hunt for bugs.

## When this runs

Two entry points:

- **`/prune-comments`** — the user invokes it directly. Scope is resolved below.
- **The final step of `session-review-loop`** — that skill reads this file and follows these steps
  once its review rounds have terminated, scoped to the diff the loop produced, using the merge-base
  it already established. In that mode there is no separate scoping pass and no round of its own:
  prune, verify, hand the report back for the loop's write-up.

## Scope

Default scope is the **working diff** — comments in code this branch touched.

```bash
git rev-parse --show-toplevel
git rev-parse --abbrev-ref HEAD
git merge-base HEAD origin/main 2>/dev/null \
  || git merge-base HEAD origin/master 2>/dev/null \
  || git merge-base HEAD origin/develop 2>/dev/null
git diff <merge-base>...HEAD --name-only
git diff --name-only          # uncommitted
git diff --name-only --cached  # staged
```

Review the union of those file lists, and within each file only lines the diff added or changed.
Comments in untouched regions are out of scope — leave them.

Overrides:
- `/prune-comments <paths>` — review exactly those files or directories in full, ignoring the diff.
- `/prune-comments --all` — every source file in the repo. Confirm with the user before starting,
  and warn that this produces a large diff across code they did not touch.

If the working directory is not a git repo, require explicit paths.

## Delete these

- **What-narration** — the comment restates the line or block below it.
  `// increment the counter`, `# loop over users`, `// set loading to true`
- **Conversation history** — the comment refers to a prompt, ticket, request, or change event.
  `// added for the onboarding flow`, `// fixed per review`, `// changed to handle the new shape`,
  `// NEW:`, `// updated 2026-04-01`
- **Section banners with no information** — `// ---- helpers ----`, `// imports`, `// constructor`
- **Restated signatures** — a docblock whose every line repeats the parameter names and types
  already in the signature, adding no constraint, unit, or contract.
- **Forward references to tickets** — a comment pointing at work that has not happened yet, in any
  tracker format: `// FW-3838 will handle this`, `// deferred to PROJ-123`, `// see CU-8a2f1x`,
  `// blocked on #412`, `// follow-up ticket coming`. The code cannot be read against a ticket that
  does not exist yet, and these outlive their tickets. Delete the whole comment when the reference
  is all it says; strip only the reference when the rest of the line states a real constraint.
  This takes precedence over the `TODO`/`FIXME` keep-rule below: a `// TODO: FW-3838` with no
  substance goes, while `// TODO: unbounded if the feed exceeds 10k rows` stays — reworded without
  its ticket id if it carried one.
- **Commented-out code** — dead code kept "just in case". Delete it; git has it.
- **Redundant type notes** in typed languages — `// string` above a `: string`.

## Keep these

Never remove:

- A non-obvious constraint, tradeoff, workaround, or gotcha not recoverable from the code
  (`// retrying because the vendor API silently drops writes under load`).
- Anything load-bearing for a tool: `eslint-disable`, `ts-expect-error`, `# noqa`, `# type: ignore`,
  `#pragma`, `#region`, `nolint`, codegen markers, `<auto-generated>` headers.
- License and copyright headers.
- `TODO`, `FIXME`, `HACK`, `XXX` markers whose text states a real problem — these are trackable
  signals, not prose. A marker that only points at a future ticket is deleted; see above.
- Public API documentation that carries contract information a caller cannot see from the signature:
  units, ranges, nullability, thrown exceptions, ordering guarantees, side effects. XML doc comments,
  JSDoc, and docstrings on public surfaces are kept when they do this. Trim only the lines inside
  them that merely restate the signature.
- Anything inside a string literal, regex, or generated file — verify a match is a real comment
  before editing it.

When a comment is genuinely ambiguous — it might encode a why you cannot verify — keep it and list
it under *Kept, uncertain* in the report. Silence is cheaper than deleting knowledge.

## Rename instead of delete

When a comment exists only because a name is poor, the fix is the rename, not just the deletion.
Apply the rename **only when the symbol's scope is provably local** — a local variable, a parameter,
or a private member with all references inside the file you are already editing. Verify with a grep
across the repo before renaming.

If the symbol is exported, public, part of an interface, a serialized field, or referenced from other
files: **do not rename**. Delete the comment if it is pure what-narration, and note the bad name
under *Rename suggestions* in the report for the user to decide.

## Steps

1. Resolve scope as described above. State the repo path, branch, and how many files are in scope.
2. Read each in-scope file. Do not rely on the diff alone — a comment's fate depends on the code
   around it.
3. For each comment in scope, decide: delete, keep, keep-uncertain, or rename-and-delete.
4. Apply the edits file by file. After any multi-edit sequence in a file, re-read it before the next
   edit — never target line numbers from a pre-edit view.
5. Verify. Run the project's type check or build, and the test suite for the touched area:
   - TypeScript: `tsc --noEmit` (or the project's typecheck script)
   - .NET: `dotnet build`
   - Python: the project's linter and `pytest` on affected paths
   A comment deletion should never break anything; if it does, a tool directive was removed or a
   rename was incomplete. Restore it and re-verify.
6. Report. Never commit.

## Report

```
Pruned N comments across M files.

<file:line>  deleted   what-narration      "// increment the counter"
<file:line>  deleted   history             "// added for the billing flow"
<file:line>  deleted   forward-ticket      "// FW-3838 will handle this"
<file:line>  trimmed   forward-ticket      ticket id stripped, constraint kept
<file:line>  renamed   d -> daysUntilDue   comment deleted, symbol was file-local

Kept, uncertain (N)
<file:line>  "<comment>" — may encode a constraint I could not verify

Rename suggestions (N) — symbol is public, your call
<file:line>  `flag` -> `isEligibleForRefund`

Verification: <build/typecheck result>, <test pass count>
```

Keep the report to what changed and why. If nothing qualified for removal, say so in one line.
